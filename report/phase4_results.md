# Phase 4 — 3D EKF Performance and Accuracy Results

## Scope and evidence status

This report describes the initial **local Windows** experiment for the 3D radar EKF and the matching synthetic accuracy evaluation. The [historical report](Final_report_draft.md) describes a 2D filter and a different process-launch benchmark; its numbers must not be combined with these measurements as if they came from the same implementation or experiment.

The current evidence does **not** establish a controlled Linux–Windows comparison. Linux GitHub Actions runs verify functionality on an Ubuntu runner, whereas the results below were measured on a different local Windows machine. Hardware, OS, background activity, filesystem, and environment differ. The Linux CI benchmark is a smoke test, not controlled performance evidence.

The original Windows [manifest](../results/phase4/windows-local-20261116/manifest.json), [raw samples](../results/phase4/windows-local-20261116/samples.csv), and [summary](../results/phase4/windows-local-20261116/summary.csv) are preserved in the repository. The separate [accuracy evaluation](../results/phase4/windows-local-20261116/accuracy.json) was regenerated later with explicit ground-truth segment labels; its measurement input and sequential executable hashes were checked against the original benchmark manifest. The manifest records input and executable SHA-256 hashes, but the run used a checkout with uncommitted Phase 4 changes; a source-to-binary match has not been independently established. This historical run predates subsequent benchmark methodology changes and must not be described as having used them.

## Workload and environment

The input is the seed-42 synthetic radar scenario generated by [`generate_3d_scenario.py`](../common/generate_3d_scenario.py): three tracks, 600 observations per track, irregular intervals, deterministic observation gaps, and straight, acceleration, turn-like, and post-turn segments. The filter uses range, azimuth, and elevation; ground truth is reserved for evaluation.

The native application uses a 3D nine-state EKF, mapped shared memory, persistent processes, and event-based synchronization on Windows. Tracks are assigned to workers by ID, preserving state across batches. The [measurement protocol](../docs/phase-4-measurements.md) explains platform implementation and reproducibility.

| Recorded property | Local Windows experiment |
|---|---|
| OS | Windows 11, reported as build `10.0.26300` |
| Hardware | Lenovo 21CUS07000; AMD Ryzen 5 5600U, 6 cores / 12 logical CPUs; 33,099,800,576 bytes RAM |
| Power plan | Balanced |
| Build | MinGW g++ 15.1.0, C++17, `-O2`; native binary linked statically with `-lpsapi` |
| Matrix | 1 and 3 selected tracks; quarter, half, and full selected observations; batches of 32 and 512; 1, 2, 4, and 8 workers |
| Sampling | One session; one warm-up and three measured native invocations for each of 48 configurations, producing 144 samples |
| Source state | Checkout `18de85d` with uncommitted Phase 4 changes, as recorded in the manifest |

The harness sorts each workload by timestamp and track ID, preserves each track's observation order, and uses the same workload for all worker counts in a configuration. Every warm-up and measured output is checked against the sequential 3D driver. The reported speedup divides the median end-to-end latency of the **one-worker native process** by that of the tested native worker count. It is not speedup against the sequential driver.

## End-to-end performance

For all 1,800 observations across three tracks, the locally saved summary and all 144 underlying samples were checked: each summary median equals the median recomputed from its three samples. Median elapsed time in milliseconds and the corresponding speedup are:

| Batch size | Workers | Median (ms) | Speedup vs one native worker |
|---:|---:|---:|---:|
| 32 | 1 | 236.191 | 1.000× |
| 32 | 2 | 330.824 | 0.714× |
| 32 | 4 | 529.662 | 0.446× |
| 32 | 8 | 1,399.410 | 0.169× |
| 512 | 1 | 172.302 | 1.000× |
| 512 | 2 | 175.291 | 0.983× |
| 512 | 4 | 208.467 | 0.827× |
| 512 | 8 | 344.389 | 0.500× |

All measured multi-worker medians in this table exceed their same-batch one-worker baseline. With only three independent measured invocations per configuration in one session, the table is descriptive; it does not establish how the application performs on other data or machines. The larger batch had a lower median at each listed worker count, but this experiment alone does not isolate the cause.

Elapsed time covers the whole native invocation, including startup, file I/O, mapping, worker launch, per-call logging, synchronization, worker shutdown, and output. Separate recorded launch, first-batch, later-batch, and shutdown durations help inspect overhead, but later-batch time still includes synchronization, scheduling, and logging. Launch is process-creation time and does not prove workers are ready. The stages do not sum to full elapsed time because setup and output include additional work.

For illustration, the mean process-launch duration for this 1,800-record workload was approximately 13.6 ms for one worker and 106.3 ms for eight workers with batch size 32; the mean later-batch duration rose from approximately 1.56 ms to 19.89 ms per batch. The timings are consistent with substantial process and synchronization overhead, but they do not separately attribute the observed slowdown to any single mechanism.

## Tracking accuracy

The saved accuracy evaluation was regenerated using the original sequential binary and matching seed-42 measurements, together with separate synthetic ground truth carrying explicit segment labels. It is a separate evaluation, not an output captured during the historical timing run. The all-row figures include prediction-only rows during missing observations and use Euclidean vector RMSE:

| State | All-row RMSE | Missing-observation RMSE |
|---|---:|---:|
| Position | 20.774 m | 24.252 m |
| Velocity | 25.832 m/s | 36.470 m/s |
| Acceleration | 6.451 m/s² | 7.055 m/s² |

| Motion segment | Position RMSE (m) | Velocity RMSE (m/s) | Acceleration RMSE (m/s²) | Rows |
|---|---:|---:|---:|---:|
| Straight | 21.631 | 45.199 | 8.524 | 450 |
| Acceleration | 18.876 | 12.977 | 5.110 | 450 |
| Turn | 19.833 | 14.238 | 5.690 | 450 |
| Post-turn | 22.555 | 15.974 | 5.942 | 450 |

For the 1,677 available observations, raw XY RMSE was 52.535 m; the existing 2D baseline was 24.069 m and the 3D EKF was 19.443 m on those same observations. The baseline assumes constant Cartesian measurement noise, whereas conversion from radar range and angles produces range-dependent Cartesian uncertainty. This comparison is illustrative and does not establish an optimally tuned baseline or superiority across datasets.

Position normalized estimation error squared (NEES) averaged 2.621 for available and 2.861 for missing rows. The fraction inside the nominal 95% position ellipsoid was 97.4% and 94.3%, respectively. These time-series samples are correlated and the synthetic motion does not exactly follow the stochastic model. The figures are diagnostics, not independent-sample confidence intervals or proof that the covariance is calibrated.

## Resource measurements and remaining work

Each sample includes whole-lifetime parent CPU, summed worker CPU, parent peak memory, and the largest individual worker peak. Linux `getrusage` and Windows process accounting have different definitions and resolution; `-1` means unavailable. Shared pages may appear in multiple processes, so these values should not be added as unique physical memory. They are available in the raw sample file, but no comparative resource conclusion is made here.

Before final submission, repeat the workload under documented comparable Linux and Windows conditions. Record the OS, hardware, compiler and flags, dataset and binary hashes, power settings, and exact source state. Use independent runs and report variability; do not claim a general OS advantage or speedup without measurements that support it. The historical rubric's 15-call requirement versus 12 explicitly listed Windows APIs also remains an instructor clarification item.
